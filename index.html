OTTO Sport AI · 2021 – 2026 · Technical owner

League scheduling engine

The engine that assigned every game in a league to a date, time, and field with conflict checks, on a youth sports platform of 50+ independently deployed microservices.

  1. Problem

    League admins told us building a season schedule by hand took days. A single grouping could hold thousands of games, and each one needed a date, time, and field that fit the league's settings, such as games per team, time windows, game length, field lights, and coach conflicts, without double-booking anyone.

  2. My role

    I worked on the original engine, then designed and owned the improved version. I ran the technical discussions, split the approved design into tickets for 2 to 3 engineers, reviewed their pull requests, and walked them through the business decisions and architecture.

  3. 5 minute slots

    The old engine placed games minute by minute, back to back, so a 1:00 to 2:00 game was followed by 2:01 to 3:01. I proposed moving to 5 minute slots, 288 in a day, and talked it through with product owners. A 60 minute game now just needs the first 12 open slots in a row inside the time window the admin picks. That made placement much faster, gave cleaner start times, and made a switch to 30 minute increments a small change. The platform then moved all game creation to 5 minute increments.

  4. Background jobs

    Ran each grouping as its own Bull job on Redis instead of holding up the frontend. Admins kept using the platform while a schedule generated, jobs could be retried, and the app could check each job's status. It also made room for a product request to let admins preview the matchups before creating the schedule.

  5. Matchups

    Redesigned the existing round robin matchup generator with the Strategy pattern so linked and unlinked groupings shared one flow.

  6. Result

    Admins went from days of building schedules by hand to minutes. Generation dropped from 30+ seconds to about 5 on 1,000+ game stress tests, and rebuilding the legacy V1 features in V3 helped move the last 3 large clients off V1.

  7. Looking back

    Game creation reused an existing function that also created events, referee templates, and game history entries. We were on a MongoDB version without transactions, so a failed run was cleaned up by its instruction ID, and that cleanup could fail too. If I did it again, I would split game creation out first. It would have been faster to build and change, faster at generating schedules, and a lot less bulky.

Embeddable schedule and standings widgets

Schedule and standings widgets that organizations placed on their own websites.

  1. Problem

    To share a schedule, organizations had to send families to the portal, print pages, or run their site on the Demosphere CMS.

  2. My role

    I owned the widgets alongside the scheduling engine.

  3. Embeds

    Organizations set up a widget configuration and got a public link to embed on their site as an iframe. Each visit hit a public NestJS endpoint that read that configuration and served the schedule or standings as HTML and CSS with Turbo.

  4. Tables

    Added sorting, filtering, and search inside the schedule and standings tables, and linked them together so clicking a team or standings opened the right page.

  5. CMS

    Extended the Demosphere CMS, which was built in Ruby, so organizations with sites on it could add the new widgets too.

  6. Contracts

    Kept API contracts and migrations backward compatible across independently deployed services, since the widgets lived on organizations' own websites.

  7. Result

    Every organization using the scheduling product had the widgets, so schedules lived on its own site instead of the portal or printed pages.
